# Жайқал — переход бэкенда на Firebase Authentication

## Контекст

Сейчас в репозитории находится **только бэкенд** проекта Жайқал:

- Ktor;
- PostgreSQL;
- Flyway;
- собственная регистрация и вход по email/паролю;
- собственные JWT access-токены и refresh-токены;
- API растений, устройств и телеметрии;
- отдельная авторизация ESP32 через Device Token.

Клиентского приложения в этом репозитории пока нет. Не нужно создавать Android-, iOS- или KMP-клиент.

Нужно заменить собственную пользовательскую авторизацию на **Firebase Authentication**, сохранив существующую бизнес-логику бэкенда.

Целевая схема:

```text
Будущий клиент
    -> получает Firebase ID Token
    -> отправляет Authorization: Bearer <Firebase ID Token>
    -> Ktor проверяет токен через Firebase Admin SDK
    -> Firebase UID сопоставляется с внутренним users.id UUID
    -> бизнес-логика работает с внутренним UUID

ESP32
    -> отправляет существующий Device Token
    -> Ktor проверяет его существующим способом
```

Firebase на этом этапе используется **только для Firebase Authentication**.

Не подключать:

- KMP-клиент;
- Android- или iOS-клиент;
- Firebase Cloud Messaging;
- Firebase Crashlytics;
- Firestore;
- Realtime Database.

---

## Общие правила

1. Сначала изучи репозиторий и прочитай `AGENTS.md`, если он существует.
2. Адаптируй названия классов и пакетов к существующей архитектуре.
3. Не переписывай API растений, устройств и телеметрии.
4. Не меняй формат телеметрии от ESP32.
5. Не заменяй Device Token устройства на Firebase Authentication.
6. Не изменяй уже применённые Flyway-миграции — создавай новые.
7. Не удаляй существующие таблицы и данные без явного разрешения.
8. Не добавляй Firebase service account JSON и другие секреты в Git.
9. Не логируй Firebase ID Token, Device Token и секретные ключи.
10. После каждого шага запускай подходящие тесты.

# Шаг 2. Добавить Firebase Admin SDK

Добавь Firebase Admin SDK в JVM-бэкенд.

Создай отдельные компоненты:

```kotlin
interface FirebaseTokenVerifier {
    suspend fun verify(idToken: String): VerifiedFirebaseToken
}

data class VerifiedFirebaseToken(
    val uid: String,
    val email: String?,
    val emailVerified: Boolean,
)
```

Названия можно адаптировать к стилю проекта.

Нужны:

- интерфейс `FirebaseTokenVerifier`;
- production-реализация через Firebase Admin SDK;
- fake-реализация для тестов;
- инициализация Firebase Admin при запуске;
- конфигурация через переменные окружения.

Используй:

- Application Default Credentials в production;
- либо путь из `GOOGLE_APPLICATION_CREDENTIALS`;
- `FIREBASE_PROJECT_ID`, если он требуется текущей конфигурации.

Firebase Admin должен инициализироваться один раз.

Если проверка токена выполняет блокирующую операцию, вынеси её с event loop на подходящий dispatcher.

При отсутствии обязательной конфигурации приложение должно завершаться с понятной ошибкой.

Не добавляй service account JSON в репозиторий.

# Шаг 3. Подготовить базу данных

Не заменяй внутренний `users.id UUID` на Firebase UID.

Внутренний UUID должен продолжить использоваться:

- во внешних ключах;
- в растениях;
- в устройствах;
- в настройках;
- в телеметрии;
- в проверках владельца.

Добавь новой Flyway-миграцией поддержку внешнего идентификатора пользователя.

Предпочтительный вариант — отдельная таблица:

```sql
user_identities
---------------
id UUID PRIMARY KEY
user_id UUID NOT NULL REFERENCES users(id)
provider VARCHAR NOT NULL
external_subject VARCHAR NOT NULL
created_at TIMESTAMP NOT NULL

UNIQUE(provider, external_subject)
UNIQUE(user_id, provider)
```

Для Firebase:

```text
provider = firebase
external_subject = Firebase UID
```

Если архитектуре проекта лучше соответствует хранение `firebase_uid` непосредственно в `users`, это допустимо, но решение нужно объяснить в документации.

Требования:

- существующие пользователи и связи не должны пропасть;
- `password_hash` и refresh-токены пока не удалять;
- новые Firebase-пользователи не должны требовать `password_hash`;
- миграция должна применяться и на чистой, и на существующей базе;
- для Firebase UID должно существовать не более одной внутренней учётной записи.

## Сопоставление существующих пользователей

Не связывай Firebase-пользователя с существующей записью только по совпадению email.

Реализуй один из безопасных вариантов:

1. Если реальных пользователей ещё нет — автоматически создавать внутреннего пользователя после первого валидного Firebase-токена.
2. Если пользователи уже существуют — подготовить явный административный или миграционный механизм сопоставления.

Выбранное поведение должно задаваться конфигурацией, например:

```text
FIREBASE_AUTO_PROVISION_USERS=true|false
```

При выключенном auto-provisioning неизвестный Firebase UID должен получать понятный отказ, а не новую учётную запись.

# Шаг 4. Реализовать Firebase authentication provider для Ktor

Добавь отдельную Ktor-аутентификацию для пользовательских запросов.

Алгоритм:

1. Получить заголовок `Authorization`.
2. Убедиться, что используется схема `Bearer`.
3. Передать ID Token в `FirebaseTokenVerifier`.
4. Проверить токен через Firebase Admin SDK.
5. Получить Firebase UID.
6. Найти соответствующий внутренний `users.id`.
7. При разрешённом auto-provisioning создать пользователя и identity.
8. Создать principal.
9. Передать внутренний UUID существующей бизнес-логике.

Principal должен содержать как минимум:

```kotlin
data class UserPrincipal(
    val userId: UUID,
    val firebaseUid: String,
    val email: String?,
    val emailVerified: Boolean,
)
```

Обработай:

- отсутствующий заголовок;
- неверную Bearer-схему;
- пустой токен;
- некорректную подпись;
- неверный project/audience/issuer;
- истёкший токен;
- отключённого пользователя;
- отозванный токен, если включена проверка revocation;
- Firebase UID без внутренней записи при выключенном auto-provisioning;
- конфликт уникальности при одновременном первом входе.

На ошибки аутентификации возвращай `401 Unauthorized`. Не раскрывай клиенту внутренние подробности проверки.

---

# Шаг 5. Перевести существующие маршруты

Переведи защищённые пользовательские маршруты на новый Firebase provider.

Проверь как минимум:

- профиль пользователя;
- растения;
- пользовательские устройства;
- настройки;
- чтение телеметрии;
- уведомления и правила полива, если они уже реализованы.

Все проверки владельца должны по-прежнему работать через внутренний `userId`.

Не меняй:

- маршруты приёма телеметрии от ESP32;
- Device Token;
- привязку физического устройства;
- формат запросов от микроконтроллера.

Если в проекте есть разные auth providers, дай им однозначные названия, например:

- `firebase-user`;
- `device-token`.

# Шаг 6. Отключить выдачу собственных пользовательских токенов

После перевода защищённых маршрутов старые endpoints:

- `/register`;
- `/login`;
- `/refresh`;
- `/logout`;

не должны продолжать выдавать собственные access- и refresh-токены.

Выбери безопасный вариант с учётом совместимости:

- удалить маршруты, если ими никто не пользуется;
- либо временно отвечать `410 Gone` с нейтральным сообщением;
- либо оставить их только за явно отключённым feature flag.

Не удаляй на этом этапе:

- старые Flyway-миграции;
- таблицу refresh-токенов;
- `password_hash`;
- старые пользовательские данные.

Физическую очистку нужно выполнять позже отдельной миграцией после подтверждения, что legacy-авторизация больше не нужна.

Удалить из активной конфигурации и DI:

- генератор пользовательских JWT;
- проверку собственных пользовательских access-токенов;
- сервис обновления refresh-токенов;

но только если они не используются для Device Token или других механизмов.

# Шаг 7. Добавить служебные endpoints

Если в проекте ещё нет аналога, добавь:

```http
GET /api/v1/auth/me
Authorization: Bearer <Firebase ID Token>
```

Ответ должен возвращать данные внутреннего пользователя, необходимые будущему клиенту, например:

```json
{
  "id": "internal-user-uuid",
  "email": "user@example.com",
  "emailVerified": true
}
```

Не возвращай:

- Firebase ID Token;
- Firebase UID без реальной необходимости;
- внутренние auth claims;
- password hash;
- service account данные.

Также добавь или сохрани health-check, который не раскрывает конфигурацию Firebase.

# Шаг 8. Добавить тесты

Тесты не должны обращаться к реальному Firebase.

Используй fake `FirebaseTokenVerifier`.

## Тесты аутентификации

Проверь:

- запрос без токена получает `401`;
- пустой токен получает `401`;
- некорректный токен получает `401`;
- истёкший токен получает `401`;
- корректный токен создаёт правильный principal;
- Firebase UID сопоставляется с правильным внутренним UUID;
- email и `emailVerified` корректно попадают в principal;
- неизвестный UID отклоняется при выключенном auto-provisioning;
- неизвестный UID создаёт пользователя при включённом auto-provisioning;
- повторный запрос не создаёт дубликат;
- параллельные первые запросы не создают двух пользователей.

## Регрессионные тесты

Проверь:

- пользователь видит только свои растения;
- пользователь не получает доступ к чужому растению;
- пользователь видит только свои устройства;
- пользователь не получает доступ к чужому устройству;
- чтение телеметрии работает;
- ESP32 продолжает отправлять телеметрию по Device Token;
- неверный Device Token по-прежнему отклоняется;
- старые auth endpoints больше не выдают JWT;
- миграции применяются на чистой базе.

Если в проекте настроены Testcontainers, используй PostgreSQL Testcontainer для integration-тестов.

Обнови:

- `.env.example`;
- README;
- Docker Compose, если он используется;
- конфигурацию CI;
- production deployment documentation;
- `docs/firebase-auth-migration.md`.

Документируй переменные:

| Переменная | Назначение |
|---|---|
| `FIREBASE_PROJECT_ID` | Firebase project ID |
| `GOOGLE_APPLICATION_CREDENTIALS` | Путь к service account JSON для локальной среды |
| `FIREBASE_AUTO_PROVISION_USERS` | Разрешить создание внутреннего пользователя после первого валидного токена |
| `FIREBASE_CHECK_REVOKED_TOKENS` | Проверять отзыв ID Token, если поддерживается выбранной реализацией |

Не помещай реальные значения секретов в `.env.example`.

Добавь ручную инструкцию:

1. Создать Firebase-проект.
2. Включить нужные способы входа в Firebase Authentication.
3. Создать credentials для серверного окружения.
4. Настроить Application Default Credentials или `GOOGLE_APPLICATION_CREDENTIALS`.
5. Передать `FIREBASE_PROJECT_ID`.
6. Перезапустить сервер.
7. Получить тестовый Firebase ID Token вне бэкенда.
8. Проверить `GET /api/v1/auth/me`.

Бэкенд не должен самостоятельно логинить пользователя в Firebase по email и паролю. Этим позже займётся клиент.

## Критерии готовности

Задача выполнена, когда:

- Ktor принимает Firebase ID Token в Bearer-заголовке;
- токен проверяется через Firebase Admin SDK;
- Firebase UID сопоставляется с внутренним `users.id UUID`;
- существующие внешние ключи продолжают работать;
- защищённые пользовательские endpoints используют новый principal;
- собственные JWT и refresh-токены больше не выдаются пользователям;
- ESP32 продолжает использовать Device Token;
- API растений, устройств и телеметрии не сломано;
- неизвестные Firebase-пользователи обрабатываются согласно конфигурации;
- тесты не требуют подключения к реальному Firebase;
- миграции работают на чистой и существующей базе;
- секреты отсутствуют в репозитории и логах;
- README содержит инструкции по настройке Firebase для бэкенда.
